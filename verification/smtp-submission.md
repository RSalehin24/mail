# SMTP submission and Sent storage

Clients use `mail.rsalehin24.me`: IMAP 993 with TLS, SMTP 587 with mandatory
STARTTLS, full mailbox address and the same mailbox password for both protocols.
The SMTP envelope, From and any Sender header must identify the authenticated mailbox.
A supplemental awk check closes Maddy 0.9.6’s From-or-Sender fallback; it accepts
a bare address or a display name with an angle-bracket address.
The website has no compose screen. Provider credentials stay on the server.

Enable saving sent messages in the account's server IMAP **Sent** folder (for
Thunderbird, Copies & Folders → Place a copy in → this account's Sent folder;
for Apple Mail, Mailbox Behaviors → Sent Mailbox → the server Sent folder).
Maddy does not append an automatic second copy. Saving can happen after successful
queue submission, before remote delivery. A Sent copy does not confirm receipt.
Clients with sent-copy saving disabled retain no sent copy. Gmail web Send As
stores its own copy in Gmail, not this account's IMAP Sent folder; use an IMAP
client to retain sent mail on this server.

The pinned production-compatible Maddy 0.9.6 configuration is generated by
`shared/submission.py`. It uses `import /data/submission-relay.conf`, `submission`,
`authorize_sender`, a shell-free `/usr/bin/awk` identity check, `target.queue` and `target.smtp` with `starttls yes` and normal
certificate verification. The queue lives under `/data/submission-queue`; the
provider include, pending synchronization record and rollback include are mode
0600 in the same root-owned tree. Never copy them into public artifacts.

Provider saves require recent administrator authentication. The root helper
validates the restricted credential grammar, atomically writes the include,
validates with the selected 0.9.6 binary, restarts Maddy and restores the previous
include on failure. A durable rollback and pending revision survive interruption.
Reconciliation compares that revision to the committed dashboard database before
keeping the new include or restoring the previous one. Errors are returned to the
administrator without credentials. Changing provider settings briefly restarts
mail services and may disconnect clients. TLS 465 is no longer a provider option.

Full host backups quiesce Maddy and capture the entire Maddy data directory,
including queue metadata and bodies, credential databases, every IMAP folder,
message bodies and the restricted provider include. Keep `maddy_message_paths` limited to the IMAP body store (`messages`); the queue
is covered by the whole-tree backup and is not an IMAP body store. Full-host recovery restores
that tree before Maddy starts. Replaying a restored queue may resend mail already
accepted after the snapshot; inspect the queue before starting a recovered host.
The dashboard's **Restore mail data** merges stored IMAP messages and folders;
it deliberately does not replay outbound jobs or replace current credentials.

Verification uses private synthetic SMTP/IMAP data with pinned Maddy 0.9.6 and
loopback ports. `tests/maddy/test_submission.py` checks authentication/TLS/sender
restrictions, successful delivery, 451 persistence across restart, permanent
rejection/bounces, certificate/STARTTLS failures, exactly one client-created Sent
copy, second-session visibility and offline data-tree restoration. Unit/API tests
cover restricted inputs, credential secrecy, configuration and synchronization
failure. Live deployment and recipient receipt are recorded separately; isolated
passes alone do not establish either.

The live rollout and recipient-confirmed test are recorded in
[the production state record](mail-admin-completion.md). Root startup verification
allows 30 seconds for a bounded cold start after backup or recovery. This extends
readiness waiting while retaining certificate and container identity checks.
